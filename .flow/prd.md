# PRD: Prism v0.2「增长闭环实战版」

日期：2026-09-17 ｜ 状态：待用户门禁裁决 ｜ 红队报告：`.flow/red-team.md`

> 无 issue tracker 配置（`docs/agents/issue-tracker.md` 不存在），PRD 按 dev-flow 降级写入本文件。

## Problem Statement

v0.1.0 交付了完整的内容工厂流水线（选题→研究→内容→四平台→裁判→人工批准→导出），但增长闭环从未在真实内容上跑过一圈（数据库实况：0 次人工批准、0 个真实发布包、14 行指标全是演示数据）。作为运营者，我现在要让第一批真实内容跑起来并从中学习，但有两个缺口：

1. **学不到东西**：一条主题只能产出一条内容（选题采纳后即锁死），没有同主题变体对照，复盘只能说「这篇表现如何」，无法回答「哪种假设更有效」——假设库因此无法迭代。
2. **不敢真用**：流水线推进（advance）没有并发保护，重复点击会重复跑 Agent、重复烧 LLM 费用（已知遗留，审查确认过无数据错乱但持续漏钱）。

## Solution

v0.2 聚焦「让第一批真实内容既能安全地跑，又能学到东西」：

1. **同主题实验变体管理**：同一选题下开设最多 3 个变体（A/B/C），每个变体是独立内容、走独立流水线、带差异化内容假设；发布后提供变体 × 平台的指标对照视图；实验结论由 Agent 提议、人工确认后写入假设库（复用既有提议门禁）。
2. **advance 内容级互斥**：同一内容的流水线推进同时只允许一个在执行，重复请求得到明确反馈而非重复扣费。

两个条件扩展项（是否纳入由门禁裁决，见 Further Notes）：公众号官方草稿接口试点、产品数据（下载/激活）回流导入。

## User Stories

1. 作为内容总编，我想在采纳一个选题后再开一个变体，以便用不同角度验证同一主题。
2. 作为内容总编，我想给每个变体指定差异化的内容假设（如「教程角度 vs 观点角度」），以便实验结论能归因到假设差异而不是随机波动。
3. 作为内容总编，我想看到同一选题下所有变体的清单与各自所处状态，以便掌控实验进度。
4. 作为内容总编，我想限制同选题变体数不超过 3 个，以免实验摊薄单变体的样本量与我的精力。
5. 作为内容总编，我想让每个变体独立走完研究→主内容→四平台→裁判→批准全流程，以便变体之间互不干扰。
6. 作为内容总编，我想在发布后并排看到同主题各变体在各平台的表现指标，以便直接比较。
7. 作为内容总编，我想看到变体对照的结论摘要（哪个变体、哪个平台、领先多少），以便不用自己算差值。
8. 作为内容总编，我想让 Growth Agent 基于变体对照结果提议假设库更新，以便学习沉淀而非留在我的脑子里。
9. 作为内容总编，我想亲自确认或驳回每条假设库提议，以便两库不被自动污染（既有门禁语义不变）。
10. 作为内容总编，我想在变体实验有结论后归档该实验（标记已学习），以便假设库与选题状态保持一致。
11. 作为内容总编，我想重复点击「推进」时得到「正在执行中」的提示而不是触发第二次 Agent 运行，以便不重复花钱。
12. 作为内容总编，我想并发推进不同内容时互不影响，以便批量运营时效率不受损。
13. 作为内容总编，我想在界面上直观看到某次推进花了多少 token / 成本（既有 runs 记录的呈现），以便控制预算。
14. 作为内容总编，我想在选题列表看到「已开 N 个变体」的标识，以便避免遗漏或超开。
15. 作为运营者，我想为同一变体在不同平台使用可区分的追踪参数，以便平台指标能精确归因到变体 × 平台（现状已满足，验收时确认不回退）。

## Implementation Decisions

- **变体建模**：变体 = 同一选题下的独立内容。contents 增加 `topic_id` 与 `variant_label`（A/B/C）两个字段；选题采纳后不再锁死（`topics.status` 语义从「二值生命周期」调整为「pending/adopted/shelved + 变体计数约束」），同一选题最多 3 条内容。历史数据无 topic_id——`data/` 为运行时产物，靠重置种子解决，不写迁移。
- **UTM 归因不变**：`utm_content` 已含唯一内容 ID + 平台后缀（`_a/_b/_c/_d`），变体作为独立内容天然可归因；严禁改动该结构（曾因共享 UTM 导致指标 4 倍虚增）。
- **对照视图**：新增「同主题变体指标对照」查询（按 topic_id 聚合各内容 × 各平台指标）；前端落在内容详情/分析页的新视图。**按前端先行流程：先出静态原型（HTML）给用户确认，再实现正式版**，视觉遵循 DESIGN.md。
- **实验结论回流**：复用 `library_proposals` 机制（Agent 提议 → 人工确认/驳回入库），不新增旁路。
- **并发互斥**：advance 路由对同一 content 加进程内互斥（单进程 Express + 同步 SQLite，in-flight 集合足够）；互斥期间重复请求返回明确的「执行中」响应（HTTP 409 语义）；不同内容互不影响。不做跨进程锁（无多实例部署计划）。
- **Agent 契约同步**：变体差异（角度/假设）进入选题采纳与研究提示词的输入；改动同步 `config/agent-contracts.yaml` 与对应 fixtures。
- **裁判与门禁零削弱**：变体内容走完全相同的裁判与人工批准硬门禁，不新增任何绕过路径。
- **GRILL 决议（2026-09-17，用户批准整包）**：
  1. 入口与上限：Topics 页已采纳选题行加「+ 开变体」；同选题存活变体 ≤3（含首个）；变体自动继承选题 campaign；标签按创建序自动分配 A/B/C。
  2. 差异化输入：开变体必填一句「变体假设/角度」→ 写入 content_hypothesis，并注入 Research Agent 提示词声明与同主题其他变体的差异点；选填受众/漏斗覆盖。
  3. 对照视图：内容详情页新增「实验对照」区块（同选题变体 × 平台累计指标并排 + 领先摘要）；Topics 页加「N 个变体」标识；指标用现有累计口径，不做观察窗口切片；前端先出静态原型给用户确认再实现。
  4. 结论回流：对照视图「提议实验结论」按钮 → Agent 生成假设库提议 → 人工确认入库（复用 proposals 门禁，不新增旁路）；不新增 topic 状态机态。
  5. 互斥反馈：服务端同一内容 advance 互斥，重复请求 409「该内容正在执行中」；前端沿用现有 busy 禁用 + 错误提示（Studio 已有 `disabled={busy}`，服务端锁堵刷新/多标签页场景）。
  6. 验收：代码交付 = 单测 + build + 原型确认；「第一批真实变体实验完成一次复盘」为发布后使用验收，不阻塞代码交付。

## Testing Decisions

- 只测外部行为（REST API 与状态机层面），不测内部实现细节；先例为 `server/tests/` 现有模式（先设 `PRISM_DATA_DIR` 到临时目录再动态 import）。
- 变体管理：选题多次采纳生成独立内容、变体数上限、变体独立走流水线、对照指标聚合正确性（含平台 JOIN 边界）、实验结论必须经 proposals 门禁。
- 并发互斥：并发 advance 同一内容只触发一次 Agent 运行（mock provider 断言调用次数），且返回执行中反馈；不同内容可并行。
- 门禁回归：变体内容同样受「无 approvals 不得发布」约束的用例。
