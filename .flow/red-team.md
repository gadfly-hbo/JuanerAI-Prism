# Red-Team: Prism v0.2 新功能规划（从规划 P1 清单选范围）

日期：2026-09-17 ｜ 评估对象：「v0.2 从 P1 清单（官方草稿接口/素材半自动生成/产品录屏辅助/评论聚合分类/回复草稿/产品数据自动回流/周复盘自动生成/同主题实验变体管理）中选功能」

## 结论

**Verdict: GO（带强制重构）**。规划可以继续，但 PRD 必须以「让增长闭环在真实内容上跑起来」为主轴——P1 清单的门控写的就是「**验证后**加入」，而数据库证据显示验证尚未发生：`approvals=0`、`publish_packages=0`、唯一一次 `metric_imports` 是种子演示数据。v0.1.0 验证的是机器可用性，不是内容价值。

## Top Kill-Assumptions（按 影响×可能性×可测成本 排序）

### KA-1（本周必测）：「可以进入 P1——P0 内容工厂已被验证」

- **Claim:** P1 的前置条件已满足，v0.2 应直接从 P1 清单选功能。
- **Steelman:** 39/39 单测通过；真实 MiniMax 全流水线（研究→主内容→四平台→裁判）跑通过；UI 三轮用户验收。机器层面确实可靠。
- **Attack:** P1 说的「验证」是内容价值被验证（发布→真实指标→复盘→假设更新），不是流水线可运行。DB 实况：2 条 PUBLISHED 是种子数据、0 次人工批准、0 个真实发布包、14 行指标全是演示导入。在没人开过的车上加装涡轮——功能做完，循环还是空的。
- **Fails if:** v0.2 交付后真实内容运营节奏依然没跑起来（无账号/无发布计划/无时间），P1 功能整体空转。
- **Evidence to get this week:** 用户一句话：平台账号是否就绪、未来 2-4 周是否有真实发布计划；`ls exports/` 看是否有过真实导出。
- **Kill criterion:** 用户确认短期无真实发布计划 → v0.2 不做 P1 功能，改为「让循环随时能真实跑起来」的封闭回路项（实验变体、回流导入链路、并发修复）。
- **Cheapest test:** GATE_PRD 时问用户 + 查 exports/ 目录。

### KA-2：官方草稿接口（L2）对四平台可行且值得

- **Claim:** 官方草稿接口是 P1 首项，能显著降低发布摩擦。
- **Steelman:** L0 导出包→人工复制粘贴确实是循环里最重的摩擦；公众号有正式的草稿箱 API。
- **Attack:** 四平台中知乎/小红书/抖音的内容写入 API 对个人号极度受限，L2 很可能只覆盖公众号一家；且 API 权限取决于账号类型（个人订阅号 ≠ 认证服务号）。只覆盖 1/4 平台时，这项投入产出比崩塌。
- **Fails if:** 少于 2 个平台对用户现有账号类型开放草稿 API。
- **Evidence to get this week:** 各平台开放平台文档核对 1-2 小时，产出「账号类型 × 草稿 API 可用性」矩阵。
- **Kill criterion:** 只有公众号可用且用户主阵地不是公众号 → 降级为公众号专属或砍掉。
- **Cheapest test:** 纯文档阅读，零代码。

### KA-3：评论聚合与分类现在有价值

- **Claim:** P1 的评论聚合分类值得进 v0.2。
- **Steelman:** C2B 线索识别是产品目标 B；community 模块已有底子（回复草稿已实现）。
- **Attack:** 当前 5 条评论全是种子数据，真实发布尚未开始，头几个月评论量趋近零。为 <10 条/周建聚合分类管线，维护成本（平台接口脆弱性）大于价值。规划自己的阶段路线也把社区/C2B 放在阶段 3。
- **Fails if:** 真实发布开始后评论量持续 <20 条/周 → 功能闲置。
- **Evidence to get this week:** 无需行动；真实发布首周手工数一次评论量即可。
- **Kill criterion:** 首月评论量低 → 移出 v0.2，推迟到阶段 3。
- **Cheapest test:** 等待观察，零代码。

### KA-4：素材半自动生成能提升内容表现

- **Claim:** 视觉素材半自动生成值得做（小红书/抖音视觉优先）。
- **Steelman:** 纯文字变体在视觉平台天然吃亏；A5 Creative Agent 在架构中已有位置。
- **Attack:** 两个硬前置未满足：(a) `src/llm` 只有文本 provider，图像生成需新增 provider 类型、选型、成本核算；(b) 质量不过人工总编这一关就是纯浪费——而「做图是不是当前瓶颈」本身未验证，总编可能更愿意手动 Canva。
- **Fails if:** 人工总编对生成素材拒绝率 >50%，或做图根本不是瓶颈。
- **Evidence to get this week:** 问总编做图是否为实际痛点；用任意工具手生成 5 张素材走一遍人工评审。
- **Kill criterion:** 手动试点拒过半 → 不进 v0.2。
- **Cheapest test:** 5 张图的手工试点。

## What's Well-Reasoned

- P1 清单自身的门控设计（「验证后加入」）是清醒的——风险只在执行时跳过这道门，清单本身没错。
- P1 实际剩余项比表面少：**周复盘自动生成**（`growth/weekly` + Growth Agent）和**回复草稿**（`community/:id/draft`）已在 v0.1.0 提前落地。
- L0/L1 发布边界纪律（不做自动发布/模拟登录/自动私信）与仓库硬规则一致，未被任何候选功能动摇。
- 确定性裁判 + 产品事实源 + 两级 IR 校验有 39 个测试兜底，能承接真实运营的容错要求。
- 「同主题实验变体管理」与阶段 2（增长闭环）直接对齐，是 P1 里最贴主轴的一项。

## What I Couldn't Assess

- 用户是否有就绪的平台账号与真实发布计划（决定 KA-1 走向）。
- 四平台草稿 API 对用户具体账号类型的可用性（KA-2 需外部文档核对）。
- Xanthil Desktop 侧产品数据（下载/激活/留存）的现有形态与可回流性（决定「产品数据自动回流」的真实成本）。
- 用户每周可投入内容运营的小时数（决定 v0.2 规模上限）。
